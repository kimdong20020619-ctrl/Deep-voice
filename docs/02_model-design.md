# 02. 모델 설계

> **2차 평가 「모델 개발 보고서」(HWP)의 원본.** 처음부터 보고서라 생각하고 쓴다.
> 상태: P1 완료 (zero-shot + 구조 개선). 학습은 P3에서 들어간다.

## 1. 설계 원칙

5개 출력을 단일 모델로 묶지 않고 **3개 헤드로 분리**한다.

근거:

- 세 문제의 성질이 다르다. 존재 탐지는 음향 이벤트 분류, 음성 위조도는 anti-spoofing,
  음악 위조도는 생성 음악 탐지로 각각 다른 사전학습 자산과 데이터가 필요하다.
- **장애 격리.** 데이터 확보가 가장 불확실한 음악 헤드가 실패해도 나머지 4개 출력은 유지된다.
  24일이라는 기간에서 이 성질은 성능보다 중요하다.
- **자원 배분이 지표에서 직접 나온다.** 실효 가중치가
  FILE 0.45 · MUSIC 0.27 · VOICE 0.18 · 존재 0.10 이므로 투자 순서가 정해진다.

## 2. 현재 구조 (P1)

```
INPUT AUDIO (16kHz mono)
│
├─ PANNs Cnn14 ─────────────────────> VOICE_PRESENT_PROB (VP)
│                                     MUSIC_PRESENT_PROB (MP)
│
└─ 게이팅 판단
   ├─ 두 성분 모두 존재 → HTDemucs 분리 ─┬─ vocals ────> DF-Arena 1B ─> VF
   │                                      └─ accomp. ───> DF-Arena 1B ─> MF
   └─ 한 성분만 존재  → 분리 생략, 원본을 해당 헤드에만 투입

FILE_FAKE_PROB = max(VP × VF, MP × MF)      (CONFIG 로 교체 가능)
```

구현: [`submit/script.py`](../submit/script.py)

## 3. Head A — 음성·음악 존재 (`VOICE_PRESENT_PROB`, `MUSIC_PRESENT_PROB`)

- 모델: **PANNs Cnn14** (AudioSet 사전학습), 32kHz 입력
- `model/panns/component_labels.json`이 AudioSet 라벨을 voice/music 두 군으로 묶어두었고,
  세그먼트 축·라벨 축 양쪽에 `max`를 건다.
- voice 군에 `Singing`·`Choir`·`Synthetic singing`·`Rapping` 등이 포함돼 있어
  **"보컬은 음성 성분"** 이라는 대회 정의와 정확히 맞는다.
- 라벨 축·시간 축 max 는 "어디든 있으면 존재"라는 정의와 맞고 **순차 혼합**
  (앞은 음악, 뒤는 음성)에도 옳게 동작한다.

**결론: 손대지 않는다.** 실효 가중치 0.10에 리더보드 1위가 이미 AUC 0.989이고,
연산 비중도 1.2%다. 성능도 비용도 이미 최적이다. 개선 여지가 최대 0.001 수준이다.

## 4. Head B — 음성 위조도 (`VOICE_FAKE_PROB`)

- 모델: **DF-Arena 1B** (`Speech-Arena-2025/DF_Arena_1B_V_1`)
  — wav2vec2-XLS-R-1B 프론트엔드 + Conformer 백엔드, 약 10억 파라미터
- 입력: 64,600 샘플(4.0375초) 세그먼트, 비중첩, 세그먼트 점수 `max` 집계
- 무음 게이트: RMS < 1e-5 이면 forward 없이 0.0

**리스크: 도메인 갭.** 모델 카드의 학습 데이터에 한국어와 전화채널이 없다.
전화채널(8kHz 대역제한)·손실압축(MP3) 샘플이 평가셋에 명시돼 있으므로 여기가 약점이다.
→ P3에서 채널·포맷 증강으로 파인튜닝. `01_data-design.md` 참조.

## 5. Head C — 음악 위조도 (`MUSIC_FAKE_PROB`) — **최대 공략점**

실효 가중치 **0.27**로 음성(0.18)보다 크고, `FILE_FAKE`(0.45)까지 여기에 물려 있다.

현재는 DF-Arena 1B를 반주 스템에 그대로 적용한다. 모델 카드 기준 학습 데이터는

```
ASVspoof 2019 / 2024 · Codecfake · LibriSeVoc · DFADD
CTRSVDD(가창 음성) · SpoofCeleb · MLAAD · EnvSDD(환경음)
```

가창·환경음까지 학습된 범용 모델이므로 "순수 음성 전용"은 아니다.
다만 **악기·반주(instrumental) 생성 음악은 목록에 없다.** 이 컬럼은 도메인 밖이다.

### 실측 증거 (2026-09-05, Colab T4)

배포 더미(음악 거의 없음, MP=0.060)에서 `MUSIC_FAKE_PROB = 0.965`가 나왔다.
Demucs가 뽑아낸 반주 스템의 잔여 잡음이 무음 게이트를 통과했고, DF-Arena가 거기에
높은 위조도를 매겼다. **신호가 아니라 잡음에 반응하고 있다.**

### 계획

1. 생성 음악 탐지 데이터 확보 (FakeMusicCaps · SONICS) → `03_license-ledger.md`
2. 전용 헤드 학습 또는 DF-Arena 파인튜닝
3. **헤드 교체 시 융합식을 반드시 함께 재설계한다** (6절)
4. 데이터 확보 실패 시: 보수적 값으로 두고 Head B에 자원 집중

## 6. 융합 — `FILE_FAKE_PROB` (실효 가중치 0.45, 단일 최대 항목)

현재 `max(VP × VF, MP × MF)`.

**문제**: EER은 순위 기반인데 존재 확률을 곱하면 순위가 왜곡된다.
`MP=0.6, MF=0.95` (0.570)가 `MP=0.99, MF=0.60` (0.594)보다 낮게 매겨진다.

**연쇄 제약**: 지금 VF와 MF는 **같은 모델에서 나와 스케일이 같다.** 그래서 `max`가 동작한다.
음악 헤드를 다른 모델로 바꾸면 두 점수 분포가 어긋나 `max`가 한쪽으로 편향된다.
→ **헤드 교체와 융합 재설계는 한 묶음이다.** 따로 실험하면 결과를 해석할 수 없다.

CONFIG로 비교 가능한 후보: `baseline` · `gated_max` · `noisy_or` · `gamma`

## 7. 추론 최적화

속도는 점수가 아니다(CPS는 존재 탐지 점수다). 60분은 통과/실패 조건일 뿐이므로
**남는 시간은 정확도에 재투자**한다.

| 항목 | 내용 | 검증 |
|---|---|---|
| 배치 패치 | 벤더 `forward`의 무조건 `unsqueeze(0)`를 조건부로 수정 | 단일 경로와 **편차 0.000000** |
| bf16 autocast | L4는 네이티브 지원 | fp32 대비 편차 0.00157 |
| 게이팅 | 성분 하나뿐이면 Demucs + DF-Arena 호출 하나가 동시에 소멸 | 0.166 → 0.087 s/오디오초 |
| 단일 루프 | 세 모델 동시 상주, 파일당 디코딩 1회 | L4 22.4GiB에 여유 |

배치 패치의 규정 검토는 [`08_compliance.md`](08_compliance.md) 3절.

### 프로파일링 (T4, 18파일 / 오디오 450초)

| 단계 | 비중 |
|---|---|
| DF-Arena (voice + music) | **70.8%** |
| HTDemucs | 27.8% |
| PANNs | 1.2% |
| 디코딩 | 0.2% |

DF-Arena가 지배적이다. `df_voice`와 `df_music`이 소수점까지 같은데,
두 스템 길이가 같아 세그먼트 수가 같기 때문이다.

## 8. 안정성 — 점수 이전의 문제

공식 베이스라인은 예외 처리가 한 곳도 없어 **1,200개 중 한 파일만 실패해도 전체가 0점**이 된다.
런타임 오류는 일일 제출 3회 중 1회를 소모하므로 비용이 크다.

- 파일 단위 `try/except` + 중립 폴백값 0.5, 실패 ID와 트레이스백을 로그에 남긴다
- 확장자 화이트리스트 제거 — 평가 데이터는 "MP3, WAV, FLAC **등**"으로만 공지됐다
- 출력값 `[0,1]` 클리핑과 비유한값 방어

T4 실측: MP3·FLAC·8kHz 전화채널·스테레오·4초 포함 **18/18 실패 0건**.
