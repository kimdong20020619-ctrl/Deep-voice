# 02. 모델 설계

> **2차 평가 「모델 개발 보고서」(HWP)의 원본.** 처음부터 보고서라 생각하고 쓴다.
> 상태: P0 — 골격만. 실제 내용은 P3(09-14 ~ 09-21)에 채운다.

## 1. 설계 원칙

5개 출력을 단일 모델로 묶지 않고 **3개 헤드로 분리**한다.

근거:
- 세 문제의 성질이 다르다. 존재 탐지는 음향 이벤트 분류, 음성 위조도는 anti-spoofing,
  음악 위조도는 생성음악 탐지로 각각 별개의 사전학습 자산과 데이터가 필요하다.
- **장애 격리.** 데이터 확보가 가장 불확실한 Head C가 실패해도 나머지 4개 출력은 유지된다.
  24일이라는 기간에서 이 성질은 성능보다 중요하다.

## 2. Head A — 음성 · 음악 존재

- 백본: AudioSet 사전학습 (PANNs CNN14 / AST / BEATs 중 택1)
- 근거: AudioSet 레이블 체계에 `Speech`·`Music`이 최상위 클래스로 존재하여 **zero-shot 성능이 이미 상당**하다
- 전략: zero-shot 기준선 확보 → 자체 합성 혼합 데이터로 분류 헤드만 경량 파인튜닝
- **P1에서 끝내고 봉인한다.** 투자 대비 수익이 가장 빨리 포화되는 축이다.

## 3. Head B — 음성 위조도

- 백본: SSL-AASIST 계열 (wav2vec2-XLSR-300M 프론트엔드 + AASIST 백엔드, 약 318M)
- 핵심 리스크: **도메인 갭.** ASVspoof 학습 모델은 전화채널·손실압축·한국어에서 성능이 급락한다
- 대응: `01_data-design.md` 3절의 채널·포맷 증강. 이것이 이 대회의 실질적 승부처다

## 4. Head C — 음악 위조도

- 대상: Suno/Udio류 생성 음악 탐지
- 리스크: 공개 데이터가 가장 부족한 축
- 축소 시나리오: 데이터 확보 실패 시 보수적 상수 또는 약한 모델로 두고 Head B에 자원을 집중한다.
  **평가 지표의 컬럼 가중치를 확인한 뒤 결정한다.**

## 5. 결합 — `fake_overall`

⬜ **미확정.** 평가 지표 확인이 선행되어야 한다.

- AUC 계열 → 순위만 보존하면 되므로 규칙 결합(`max`, `has_*` 가중)으로 충분
- 로그로스 / Brier 계열 → 확률값 자체가 점수이므로 **캘리브레이션 필수**, stacking 검토

## 6. 추론 최적화

목표 **40분 / 1,200파일** (상한 60분 대비 안전마진).

- 배치 추론, 긴 파일은 청크 분할 후 집계
- CPU 폴백 경로 유지 (평가 서버 GPU 유무 미확인)
- 가중치 전량 zip 동봉 — 런타임 다운로드 코드 금지
