# 05. 베이스라인 해부와 공략점

> 대상: 코드공유 `[Baseline_Inference] PANNs·HTDemucs·DF_Arena_1B 기반 AI 탐지` (zero-shot, 추가 학습 없음)
> 작성 2026-09-05. 실측하지 않은 추정은 **⬜ 미검증**으로 표시했다.

## 1. 베이스라인 구조

```
INPUT AUDIO
├─ PANNs Cnn14 (32kHz) ──> VOICE_PRESENT_PROB (VP)
│                          MUSIC_PRESENT_PROB (MP)
└─ HTDemucs ─┬─ vocals ────────> DF-Arena-1B ──> VOICE_FAKE_PROB (VF)
             └─ accompaniment ─> DF-Arena-1B ──> MUSIC_FAKE_PROB (MF)

FILE_FAKE_PROB = max(VP × VF, MP × MF)
```

구현 세부:

| 항목 | 값 |
|---|---|
| 세그먼트 | 64,600 샘플 (16kHz 기준 4.04초), **비중첩**, 마지막만 끝에 맞춤 |
| 집계 | 세그먼트별 확률의 **max** |
| 무음 처리 | RMS < 1e-5 이면 fake 확률 0.0 |
| PANNs 입력 | 16k → 32k 리샘플, 전 세그먼트 일괄 배치 추론 |
| PANNs 라벨 | `component_labels.json`의 voice/music 라벨군에서 **max** |
| 오프라인 | `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, 가중치 `model/` 동봉 |
| 입력 포맷 | aac, flac, m4a, mp3, ogg, opus, wav, wma (librosa 로드, mono 다운믹스) |
| 출력 | `output/submission.csv`, UTF-8, 소수 10자리 |

## 2. 평가 지표 ✅ 확정

전문은 `06_scoring-and-submission.md`. 요약:

```
Score = 0.9 × ADS + 0.1 × CPS
ADS   = 0.5×(1−File EER) + 0.2×(1−Voice EER) + 0.3×(1−Music EER)
CPS   = 0.5×Voice Presence AUC + 0.5×Music Presence AUC
```

총점 실효 가중치: **FILE 0.45 · MUSIC 0.27 · VOICE 0.18 · 존재 0.10**

> 정정: CPS를 속도 점수로 볼 여지를 열어뒀으나 **Component Presence Score**로 확정됐다.
> 속도는 점수에 반영되지 않으며 60분은 통과/실패 조건이다.

## 3. 시간 예산 — 점수가 아니라 통과 조건 ⬜

**6 vCPU / 28GB RAM / L4 22.4GiB**, 60분 / 1,200파일 = **파일당 3.0초**

베이스라인이 파일당 하는 일:

1. 오디오 로드 (존재 탐지 루프)
2. PANNs Cnn14 추론
3. **오디오 재로드** (컴포넌트 루프 — 같은 파일을 두 번 읽는다)
4. **HTDemucs 분리** ← 지배적 비용
5. DF-Arena-1B 추론 × 2, **세그먼트당 1회씩, 배치 없음**

⬜ **추정** (실측 필요): 평균 25초 가정 시 총 오디오 8.3시간. HTDemucs가 L4에서 10~15배속이면
분리에만 33~50분. → 베이스라인은 60분에 근접하거나 초과할 수 있다.

**속도가 점수가 아니므로 목표가 바뀐다.** 최소화가 아니라 **60분 안에 들어가면서 남는 시간을
정확도에 재투자**하는 것이 옳다. 게이팅으로 확보한 시간은 앙상블·TTA·더 큰 음악 모델에 쓴다.

## 4. 공략점 — 우선순위순

### 🥇 A. MUSIC_FAKE_PROB이 구조적으로 잘못됐다

DF-Arena-1B는 **음성 anti-spoofing 모델**이다. 이것을 반주(accompaniment) 스템에 그대로 적용하고 있다.
완전한 도메인 외 사용이며, `MUSIC_FAKE_PROB`은 사실상 신호가 아니다.

**`MUSIC_FAKE_PROB`의 실효 가중치는 0.27로 `VOICE_FAKE_PROB`(0.18)보다 크다.**
게다가 `FILE_FAKE = max(VP·VF, MP·MF)`이므로 음악 성분이 있는 파일의 File 판정(0.45)까지
이 헤드를 따라간다. → **실효 레버리지는 0.27을 크게 넘는다. 이 대회의 핵심이다.**

→ **생성음악 탐지 전용 헤드를 따로 만든다.** 경쟁팀 다수가 베이스라인을 그대로 쓴다면
차별화 지점이기도 하다.

### 🥈 B. HTDemucs를 모든 파일에 돌린다 — 정확도와 속도를 동시에 깎는다

- **정확도**: 분리 스템에는 Demucs 특유의 아티팩트가 남는다. anti-spoofing 모델은 이 아티팩트를
  **spoof 단서로 오인**한다 → REAL 혼합 오디오에서 위양성. 음성 단독 파일(전화채널 포함)까지
  불필요하게 분리를 거치며 신호가 훼손된다.
- **속도**: 파이프라인 시간의 대부분.

→ **PANNs 존재 확률로 게이팅한다.**

```
MP < τ_music  → 분리 생략. VF = DF(원본),  MF = 0
VP < τ_voice  → 분리 생략. MF = 음악헤드(원본), VF = 0
그 외(혼합)   → HTDemucs 분리 수행
```

오디오 유형이 음성/음악/혼합 3종이므로 분리가 실제로 필요한 파일은 일부다.
**A안이 실패하더라도 B는 단독으로 ADS와 CPS를 함께 올린다.** 가장 확실한 초기 개선이다.

### 🥉 C. 세그먼트 집계가 max다

단일 세그먼트의 이상치에 그대로 끌려간다. EER은 순위 기반이라 이런 이상치가 순위를 뒤집으면
바로 손해다. 다만 "순차 혼합"(앞은 음악, 뒤는 음성) 유형에는 max가 유리한 면도 있다.
→ 로짓 평균 / top-k 평균 / 길이 가중 평균을 비교한다. **구현 비용이 거의 0인 개선.**

### 🎯 B′. 융합식 `max(VP·VF, MP·MF)` 재설계 — 0.45짜리 항목

존재 확률을 곱하면 순위가 왜곡된다. 명백히 FAKE인 음악인데 MP=0.6이면 0.6·MF로 눌린다.
EER은 순위만 보므로 이 왜곡이 그대로 점수다.
→ 대안: 하드 게이팅 후 `max(VF,MF)` · noisy-or `1−(1−VF)(1−MF)` · 학습 융합.
**단일 최대 항목이므로 실험 대비 효과가 가장 크다. C와 함께 P1에서 처리한다.**

### D. 전화채널·손실압축 도메인 갭

DF-Arena-1B는 8kHz 대역제한 + 코덱 왕복 오디오에서 성능이 떨어진다.
→ `01_data-design.md`의 채널·포맷 증강으로 파인튜닝. P3의 본 작업.

### E. DF-Arena 추론에 배치가 없다

`predict_fake`가 세그먼트를 하나씩 넘긴다. L4 GPU가 논다.
→ 세그먼트 배치화. 순수 CPS 개선이며 위험이 없다.

### F. 오디오를 파일당 두 번 로드한다

존재 탐지 루프와 컴포넌트 루프가 분리돼 있다. 단일 루프로 합치면 I/O가 절반.

### G. 스테레오를 mono로 다운믹스

평가 데이터에 스테레오가 섞여 있다. 채널 간 차이는 생성 오디오 판별 단서가 될 수 있다.
→ 우선순위 낮음. 여력이 있으면 검토.

## 5. 전략적 함의

- **1차**: Private(= 종료 시점 Public, **분할 없음**) 상위 **15팀** 2차 진출
- **2차**: 보고서 2종 종합 평가 → 최종 **7팀** 수상 (진출 시 수상 확률 47%)
- 단, 2차의 모델 성능 점수는 `30 × (본인 Public / 진출팀 최고 Public)^N`, **N은 1~5 비공개**.
  N=5면 최고점의 95%여도 6.8점을 잃는다.

→ **"15위만 넘기면 된다"는 틀렸다.** 진출은 필요조건이고 그 뒤에도 격차가 지수로 증폭된다.
   다만 리더보드 1위 추격에 전부를 걸 이유도 없다. **15위를 확실히 확보한 뒤 보고서와 점수를
   병행해 올리는 것**이 기대값이 가장 높다.

→ Public/Private 분할이 없으므로 **리더보드 점수를 그대로 신뢰할 수 있다.** 검증셋 과적합 걱정 없이
   리더보드를 기준으로 판단하되, **일 3회 제한**이 병목이다.

→ `01_data-design.md`·`02_model-design.md`를 P0부터 보고서 원본으로 관리하는 이유가 이것이다.
