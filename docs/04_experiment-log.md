# 04. 실험 로그

> **일일 제출 3회 제한.** 변경점을 1개씩만 반영하고 결과를 여기 남긴다.
> 한 번에 여러 개를 바꾸면 무엇이 점수를 올렸는지 알 수 없고, 되돌릴 수도 없다.
>
> Public = Private = 전체 테스트 100% (분할 없음) → 리더보드 점수를 그대로 신뢰할 수 있다.

## GPU 검증 (2026-09-05, Colab **Tesla T4**)

평가 서버는 L4 다. T4 는 Turing 이라 **bf16 텐서코어가 없어** DF-Arena 가 에뮬레이션으로 돈다.
따라서 아래 시간은 **비관적(안전한 방향)** 이다. L4 에서의 실측은 ⬜ 미확보.

### 기능 검증 — 전부 통과

| 항목 | 결과 | 의미 |
|---|---|---|
| 가중치 SHA-256 | 배포 `SHA256SUMS.txt` 와 3개 전부 일치 | HF 리비전 `fb6ce85` = 대회 배포본 |
| 포맷 내성 | **18/18, 실패 0건** | MP3·FLAC·8kHz 전화채널·스테레오·4초 전부 디코딩 |
| 배치 패치 | **최대 편차 0.000000** | 단일 경로와 완전 동일. 수학적 동등성 실증 |

**시간의 71%가 DF-Arena 다. Demucs 가 아니다.**
`df_voice` 와 `df_music` 이 소수점까지 같다 — 두 스템 길이가 같아 세그먼트 수가 같기 때문이며,
모든 파일에서 1B 모델을 정확히 두 번씩 완전히 돌리고 있다는 뜻이다.

`panns` 가 1.2% 라는 것도 중요하다. 존재 탐지(실효 가중치 0.10, 이미 AUC 0.989)는

### `demucs_gating` 효과

| | s/오디오초 | 비고 |
|---|---|---|
| OFF | 0.166 | 베이스라인과 동일 구성 |
| ON (시험세트) | **0.087** | 1.92배. 분리 생략 15/18 |

게이팅이 켜지면 **Demucs 와 DF-Arena 호출 하나가 동시에** 사라진다
(빈 스템이 무음 게이트 `RMS < 1e-5` 에 걸려 forward 없이 0.0 반환).

**단, 1.92배는 낙관적이다.** 시험세트는 전부 같은 더미(음악 없음)라 83% 가 생략됐다.
실제 평가셋은 음성/음악/**혼합** 3종이므로 생략 비율이 더 낮다.

비용 모델 (검증됨 — 시험세트 예측 0.077+오버헤드 ≈ 실측 0.087):

```
생략 0.059 · 분리 0.164 s/오디오초
83% 생략(시험세트) -> 0.087   ✅ 실측 일치
67% 생략(3종 균등 가정) -> 0.104   ← 실제 추정치
```

### ⚠️ 제출 #1 의 게이팅은 실제로 작동하지 않았다 (2026-09-06 발견)

`gate_music = 0.05` 로 설정해뒀는데, **음악 없는 파일의 `MUSIC_PRESENT_PROB` 실측값이 0.060** 이다.
임계값이 관측된 잡음바닥보다 낮으면 `music_present >= gate_music` 이 항상 참이 되어
**게이트가 한 번도 열리지 않는다.**

"음악 가중치가 0.27 로 무거우니 보수적으로" 라는 판단이었으나, 보수적인 게 아니라 **무효**였다.
1.92배 속도 이득을 실측했을 때 쓴 값은 **0.10** 이다.

→ `gate_music` 을 0.10 으로 되돌렸다. PANNs 음악 존재 AUC 가 0.989 라
   0.06(없음) 과 ~0.9(있음) 사이 간격이 넓어 0.10~0.30 구간은 안전하다. 최적값은 검증셋에서 정한다.

**교훈**: 임계값은 관측된 값의 분포를 보고 정한다. 가중치가 무겁다는 이유만으로 낮추면
안전해지는 게 아니라 기능이 꺼진다.

### 이 발견이 제출 #2 의 시간 리스크를 해소했다

`file_head: direct` 는 혼합 파일마다 DF-Arena 호출이 하나 는다. 시간 초과가 걱정이었는데,
게이트를 고치면 그보다 더 많이 절약된다.

| 구성 | 분리 생략률 | s/오디오초 |
|---|---|---|
| 제출 #1 — 게이트 무효(0.05) + `fusion` | 0% | **0.164** ← 실제 완주 확인 |
| 제출 #2 — 게이트 작동(0.10) + `direct` | 50%(보수적 가정) | **0.141** |

**완주가 확인된 구성보다 14% 가볍다.** 평가셋 평균 길이와 L4/T4 속도차를 몰라도
이 비교만으로 시간 안전이 보장된다.

→ `scripts/build_submit.py` 에 이 계산을 넣었다. 빌드할 때마다 제출 #1 기준선과 대조해
   무거워지면 경고한다. 절대 시간 추정보다 이 상대 비교가 신뢰도가 높다.

산식 검증: `0.9 × 0.6597777778 + 0.1 × 0.9893940741 = 0.6927394` ✅

### 제출 #1 분석

| | 우리 | 1위 | 차이 |
|---|---|---|---|
| Score | 0.69274 | 0.83984 | −0.14710 |
| **ADS** | **0.65978** | **0.82323** | **−0.16345** |
| CPS | 0.98939 | 0.98932 | **+0.00007** |

**완주했다.** 60분 제한을 통과했고 실패 파일도 없었다. 게이팅 판단이 옳았다.

**CPS 는 1위를 앞섰다.** 존재 탐지는 포화가 실증됐으므로 이후 완전히 봉인한다.
최대 개선 여지를 계산하면:

| 항목 | 최대 개선 | 총점 기여 |
|---|---|---|
| CPS 0.98939 → 1.0 (완벽) | +0.01061 | **+0.00106** |
| ADS 0.65978 → 0.82323 (1위) | +0.16345 | **+0.14710** |

**ADS 격차가 CPS 를 완벽하게 만드는 것보다 139배 크다.** 자원을 전부 ADS 에 넣는다.

### EER 역산 — 확정된 것과 아닌 것

```
ADS = 1 − (0.5·File + 0.2·Voice + 0.3·Music) = 0.6597777778
→ 0.5·File + 0.2·Voice + 0.3·Music = 0.3402222222
```

✅ **확정**: 가중평균 EER = **34.0%**. 1위는 17.7%. **우리 오류율이 약 두 배다.**

⬜ **미확정**: 개별 EER. 미지수 3개에 방정식 1개라 분해가 결정되지 않는다.
`File 0.34 / Voice 0.10 / Music 0.50` 도 `File 0.40 / Voice 0.10 / Music 0.40` 도 똑같이 합이 맞는다.
**음악이 범인이라는 것은 구조적 논거이지 측정값이 아니다.**

### Music EER 을 단독으로 측정하는 방법

`MUSIC_FAKE_PROB` 를 상수로 고정하면 Music EER 이 **정확히 0.5** 가 된다.
`file_head=direct` 라 FILE 이 음악 점수에 의존하지 않으므로, 나머지가 같은 두 제출을 비교하면

```
ADS(상수) − ADS(모델) = 0.3 × (Music EER − 0.5)
```

로 **Music EER 을 정확히 역산**할 수 있다. `CONFIG["music_head"] = "constant"` 가 이 진단 모드다.
이 한 번의 제출이 "음악 헤드에 며칠을 투자할 가치가 있는가"를 확정한다.

### 🔍 세그먼트 `max` 집계의 길이 편향 (2026-09-06 분석)

평가셋은 4~60초다. 세그먼트 수가 **1~15개**로 달라지는데 `max` 는 표본이 많을수록 커진다.
→ **긴 REAL 파일이 단지 길다는 이유로 높은 점수를 받는다.** EER 은 파일 간 순위이므로 그대로 손해다.

시뮬레이션 (REAL 세그먼트 오탐 6% 가정):

| 세그먼트 수 | 길이 | REAL 파일의 평균 max |
|---|---|---|
| 1 | 4초 | 0.205 |
| 4 | 16초 | 0.406 |
| 8 | 32초 | 0.545 |
| 15 | 60초 | **0.669** |

**3.3배 차이다.** 60초짜리 진짜 파일이 4초짜리 가짜 파일만큼 높은 점수를 받는다.

#### 가정 민감도 — `max` 는 거의 항상 진다

오탐률(0~12%) × 위조구간 비율(15~100%) 16칸을 훑었다.

| 조건 | max | mean | top40% |
|---|---|---|---|
| 오탐 0% / 위조 15% | **0.0407** | 0.1250 | 0.0777 |
| 오탐 6% / 위조 70% | 0.1070 | **0.0120** | **0.0120** |
| 오탐 12% / 위조 100% | 0.1280 | **0.0020** | 0.0190 |

**`max` 가 이긴 곳은 16칸 중 1칸** — 오탐률이 정확히 0이고 위조 구간이 짧을 때뿐이다.
최다 승자는 **`top25%`(7칸)**, 그다음이 `mean`(6칸).

우리 위치 추정: 가중평균 EER 34% → 오탐률이 낮지 않다. 대회 정의상 "AI로 생성된 성분"은
부분 삽입보다 성분 전체일 가능성이 높다. **그 영역에서 `max` 는 9~64배 나쁘다.**

⬜ **단, 전부 시뮬레이션이다.** 실제 DF-Arena 점수 분포는 미확인이다.
   기본값은 베이스라인(`max`)으로 두고 **검증셋에서 확인한 뒤** 바꾼다.

→ 비율 지정 top-k 를 추가했다 (`segment_topk_ratio`). 길이에 따라 k 가 함께 늘어 편향이 상쇄된다.
   자체 검사로 "max 는 길이에 따라 오르고 비율 top-k 는 덜 오른다"를 실증했다.

### 🔍 그 밖의 미검증 상수 (같은 방법으로 점검)

`gate_music` 을 잡아낸 방법 — **설정값을 실측 분포와 대조** — 을 나머지에도 적용했다.

| 상수 | 현재값 | 상태 |
|---|---|---|
| `gate_music` | 0.10 | ✅ 잡음바닥 0.060 확인 후 설정 |
| `gate_voice` | 0.20 | ⬜ **미검증** — 음성 없는 파일의 VP 를 측정한 적이 없다 |
| `silence_rms` | 1e-5 | ⬜ **의심** — 제출 #1 에서 음악 없는 더미(MP=0.060)의 Demucs 잔여물이 이 게이트를 통과해 `MUSIC_FAKE=0.965` 를 받았다. 신호가 아니라 잡음을 채점한 것이다 |

둘 다 CONFIG 로 올려 검증셋에서 스윕할 수 있게 했다.

### 계획된 A/B 순서

실효 가중치 `FILE 0.45` > `MUSIC 0.27` > `VOICE 0.18` > `존재 0.10` 순으로 레버리지가 크다.
구현 비용이 0에 가까운 것부터 소진한다.

| 순서 | 변경 | 겨냥 | 비용 | 근거 |
|---|---|---|---|---|
| #1 ✅ | 기준선 (게이팅 ON, `file_head=fusion`) | 전체 | 완료 | 0.69274 / ADS 0.65978 |
| **#2** | **`file_head`: `fusion` → `direct`** | **FILE 0.45** | 단일성분 0 / 혼합 +1회 | 아래 |
| #3 | #2 유지 + `music_head`: `none` → **`constant`** | **진단** | 음악 채점 생략분만큼 오히려 빠름 | Music EER 단독 역산. 음악 헤드 투자 여부를 확정한다 |
| **#4** | **`segment_agg`: `max` → `top25%`** | **전 항목** | 0 | 길이 편향. 가정 16칸 중 max 가 이기는 곳은 1칸뿐 |
| #5 | `gate_music` 최적값 (0.10 / 0.20 / 0.30) | MUSIC 0.27 + 속도 | 0 | 잡음바닥 위 어디가 최적인지 미확인 |
| #6 | `silence_rms` 상향 (3e-4 / 1e-3) | MUSIC 0.27 | 0 | 분리 잔여물을 채점하는 문제 |
| #7 | `short_pad`: `tile` → `zero` | 짧은 파일 | 0 | tile 이음매의 클릭이 오탐 요인 |
| 이후 | 생성 음악 선형 프로브 | MUSIC 0.27 | 학습 필요 · 추론 0 | #3 결과에 따라 결정 |

**#2에서 `direct_max` 가 아니라 `direct` 를 고른 이유**:
가장 무거운 항목(0.45)을 가장 간접적으로 구하고 있었다. 베이스라인은
16kHz를 44.1kHz로 업샘플 → Demucs 분리 → 스템 채점 → 존재확률 곱 → max 로 FILE 을 합성한다.
단계마다 모델의 학습 분포에서 멀어진다.

`direct_max = max(direct, fused)` 는 오염된 `fused` 를 그대로 통과시킨다.
음악 헤드가 신뢰할 수 없다는 구조적 의심이 있는 상태에서는 **순수 `direct` 가 그 항을 완전히 우회**한다.
`direct_max` 는 #3 에서 Music EER 을 확인한 뒤, 음악 헤드가 쓸 만한 것으로 판명될 때 다시 꺼낸다.

**#3(진단)을 성능 실험보다 앞에 두는 이유**: 남은 23일 중 음악 헤드 학습에
며칠을 쓸지 말지가 가장 큰 자원 배분 결정인데, 지금은 **근거가 추론뿐**이다.
제출 한 번으로 Music EER 을 정확히 알 수 있다면 그게 가장 값싼 정보다.
